# Front Matter

The pages around the story: the title page, copyright page, dedication, epigraph, "also
by," acknowledgments, and about-the-author. This skill fills the book's identifying
**metadata** (author first of all) and authors those **front- and back-matter pages**,
then leaves them where the packagers pick them up, so the finished EPUB, DOCX, and PDF
open with a proper title page and close with an author bio.

It runs as publishing prep, once the manuscript is settled. It never touches the
chapters — only metadata and the matter around them.

## First job: fill the metadata

The packagers build the title page from `book.json`, so the **author field is the thing
to fix** — a blank author is why books have been coming out unsigned. Set these in
`book.json` (extending the existing spec):

```json
{
  "title": "string",
  "subtitle": "string",
  "author": "string",
  "series": { "name": "string", "number": 1 },
  "publisher": "string",
  "copyrightYear": 1990,
  "rights": "All rights reserved.",
  "edition": "First edition"
}
```

`title`, `author`, and (when present) `subtitle`/`series` show on the title page. The
rest feed the copyright page. Only `title` and `author` are load-bearing for the
packagers; the others are optional. **Confirm the author name with the user — never
invent or guess it.**

## Where the matter lives

In the book project folder, a `front-matter/` folder with a manifest:

```
front-matter/
├── front-matter.json   # ordered manifest: which pieces, front vs back, in what order
├── copyright.md        # usually generated from book.json metadata (see below)
├── dedication.md       # "For …"
├── epigraph.md         # a short quotation + attribution
├── also-by.md          # the author's other titles
├── acknowledgments.md  # back matter
└── about-author.md     # back matter — author bio
```

**`front-matter.json`** tells the packagers what to render and where:

```json
{
  "front": [
    { "type": "copyright",  "file": "copyright.md" },
    { "type": "dedication", "file": "dedication.md" },
    { "type": "epigraph",   "file": "epigraph.md" }
  ],
  "back": [
    { "type": "acknowledgments", "file": "acknowledgments.md" },
    { "type": "about-author",    "file": "also-by.md" }
  ]
}
```

`front` pieces render **after the title page, before chapter 1**; `back` pieces render
**after the last chapter**. None appear in the chapter table of contents. Each piece is
a markdown file; the `type` tells the packager how to style it (a dedication is centered
and italic, a copyright page is small and left-aligned, an about-the-author gets a
heading). Omit the folder entirely and the packagers build exactly as before — front
matter is purely additive.

## The pieces

- **Title page** — generated by the packagers from `book.json` (title, subtitle, author,
  series). This skill's job is to get that metadata right, not to write a title page
  file.
- **Copyright page** — generate it from the metadata: copyright line
  (`© <year> <author>`), the rights statement, publisher, edition, a fiction
  disclaimer ("This is a work of fiction. Names, characters, and events are the product
  of the author's imagination…") when the book is fiction, and an ISBN if the user has
  one. Offer a standard block; let the user edit it.
- **Dedication** — short and personal ("For …"). **Ask; never invent one.**
- **Epigraph** — a brief quotation with attribution. **Flag permissions:** song lyrics
  and most text by authors who died within the last ~70 years are under copyright and
  may need permission; public-domain or the user's own words are safe. Surface this; the
  user decides.
- **Also by** — the author's other titles, grouped by series if relevant. Pull from the
  **series-bible** `series.json` when the book is part of a series.
- **Acknowledgments** — back matter; the user supplies who to thank. Offer to draft from
  names they give.
- **About the author** — back matter; a short third-person bio. Offer to draft from a few
  facts; keep it to a paragraph or two. (A longer marketing bio belongs with the
  back-cover/blurb skill.)

## How to build it — a guided interview

Draw it out of the user; don't fabricate identity details.

1. **Author name first.** Confirm exactly how the byline should read, and set it in
   `book.json`. This alone fixes the blank-author problem.
2. **Metadata.** Ask for subtitle, series name/number, publisher (or "self-published"),
   copyright year and holder, edition, and ISBN if any. Leave blanks rather than
   guessing.
3. **Dedication and epigraph.** Ask whether they want each; both are optional. For an
   epigraph, raise the permissions question before using anyone else's words.
4. **Copyright page.** Generate it from the metadata and show it for approval; it is
   boilerplate the user should confirm, not legal advice.
5. **Back matter.** Offer an about-the-author bio and an acknowledgments page from facts
   and names the user provides.
6. **Write the manifest.** Create `front-matter.json` in the order the user wants, then
   recap what will appear and where. Support partial runs: "just add a dedication,"
   "redo the bio," "drop the epigraph."

## Relationship to the other skills

- **epub-/docx-/pdf-packagers.** They read `book.json` for the title page and render the
  `front-matter/` pieces in manifest order (front before chapter 1, back after the last
  chapter). Build or refresh the front matter before packaging.
- **book.json.** This skill owns the identifying metadata fields it adds; the packagers
  consume them.
- **series-bible / `series.json`.** Source of the "also by" list and the series line on
  the title page for a multi-book project.
- **back-cover blurb (when built).** The marketing description and the longer author bio
  live there; the about-the-author here is the short in-book version.
- **book-machine.** Offer this as part of publishing prep, just before packaging.

## A note on what this is not

The copyright page and rights language are **standard boilerplate, not legal advice**.
Flag anything that needs the user's real-world input (legal name, ISBN, permissions for
quoted material) rather than inventing it.

## Audit log
When a run finishes, record it so there's a trail of what happened — that the skill ran,
its result, the items it went through, and the outputs it wrote. Append one entry with the
shared logger:

`python <skills-dir>/lib/audit_log.py --skill front-matter --target <book-folder> --status <PASS|FAIL|DONE|verdict> --item "<each item processed>" --output "<each file written>" --note "<one-line summary>"`

Use `DONE` when the skill has no pass/fail; otherwise its verdict (PASS/FAIL, GO/HOLD,
READY/NOT-READY, or the band). `--item` is what the run went through (usually the chapters);
`--output` is each file written (omit if read-only). Full convention: `lib/AUDIT-LOG.md`.
